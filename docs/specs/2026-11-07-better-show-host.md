# pi-better-show in the GUI (todo #129, items 2, 3 and 5)

Status: built on `feat/better-show`; pi-better-show is pinned at 0.4.0 (registry; 0.1.2 until the `tree` block, see "Notes from task: the tree block" at the end). Round 2 (below, "Round 2") adds contract v2 and moves the answered record to the server. Design of the package: `~/projects/pi-better-show/docs/specs/2026-11-07-better-show/spec.md` (D10 to D14, Hosts, pi-straw-boss GUI). Boss decisions: sb supports the package's blocks in documents and chat, restyles them to its own look, and the package follows light and dark (the light palette comes with the theme mechanism, not here).

## What the page does

- **Where a block can appear.** In an agent's message in the comms log (every base: Standard, Geek, Zen's companion log and history, a phone, a box's unit shown through operate: they all mount `gui/chat.ts`), and in a Markdown document card (`.md`, `.markdown`). An `html` document keeps its sandboxed frame; a plain text document stays text.
- **Prose and blocks.** The text is split by the package's `parse`; prose is sb's own `markdown.ts`; each block is the element of its kind fed with the block's data (`gui/blocks.ts`); a block that does not parse shows its source in code, with the reason as its tooltip. The hand-made alert callout of todo #128 is gone: an alert is `pbs-callout`. Where no block is drawn (an ally run's report) a `> [!NOTE]` quote is a plain quote.
- **Lazy.** `gui/mdbody.ts` draws every message and document as Markdown first, and only when its text holds a block (a hint: a fence of a block kind or an alert) imports `gui/blockschunk.ts` (the package's parser with `yaml`, the fourteen elements, `blocks.ts`, and `pbs.css`). No block code is in the eager bundle (`tests/imports.test.ts` asserts it); measured against main, the eager files are the same size raw (117,057 bytes) and 3 bytes smaller gzipped.
- **Density.** `compact` in the comms log, `comfortable` in a document.

## Answers

An element's `pbs-answer` is cancelled by the page (the host takes it); the element stays open while the answer is on its way, a failed delivery shows its reason under the block and leaves it open, and only a delivered answer locks the element (`answered`) and is stored.

- **Chat block** → the boss's message to that unit: `encodeAnswer(answer)` (a chip's text as it is) through the composer's input route, `POST api/sessions/<key>/input {text, as: "send", guarded: true}`. `guarded` puts it under the guards of a paired device's write (no local-only `/boss` command), because the text comes from an agent. A text that begins with `!` or `/` is never sent (the page says so): a chip's label says nothing of a shell line or a command. For a tower the same route is the boss event; a box's unit (Link operate) goes through the bridge like any composer send, with the operate guards of the box.
- **Document block** → `POST api/doc/<capability>/answer {answerId, answer, rev}` (`src/docs.ts` `answer`, routed by `control.ts` scope `doc`, only that action): `answer` is the package's `Answer` whose `ref.block` is the block (the page sets it from the block's own index), `rev` the hash of the text the page drew. Only a Markdown document takes it (a v2 `blocks` document, or a v1 text document named `.md`/`.markdown`): an HTML or plain text document is refused with 409, and so is a v1 Markdown document (409 `refused`: pi-herdr-doc-review takes no block answers, the v2 package pi-better-show does; the page still draws the blocks). The v2 owner gets the `Answer` (its `ref` set by the server to the document's display and the block). Before anything is recorded or sent the server reads the text from the owner and holds the answer to it (round 4, BSR-F003): `rev` must be the hash of the text served now (409 `stale` otherwise) and the block one the text has (409 `no_block`; `src/blockcount.ts` counts the places a block can be with the parser's own line scan, an upper bound, because the server cannot import the parser and a block that does not fit its schema has no index); a refusal at this step does not spend the answer id. An operate session never reaches it (decision 12: `doc/**` is refused in `operateroutes.ts`).
- **Answer ids.** One id is sent once: its outcome is kept for the 30 minute window and replayed, whatever else is answered meanwhile (the cache expires by time only, never by count). A send that failed outright (an exception, no outcome) is forgotten, so the same id may try again; a refusal and "not confirmed" are outcomes.
- **Answered (BS-F004).** The record is the server's: `src/answered.ts`, one file `answered.json` beside `paired.json` (mode 600, written whole by rename), at most 2,000 entries (the oldest dropped), 90 days, each answer cut to 64 fields of 1,024 characters. A key is a JSON array, so no part moves a boundary: chat `["chat", unit key, entry id, index]`, document `["doc", unit key, path (v1) or display (v2), hash of the text, index]`; it holds no capability, so it survives a restart of the server, a new capability, another device, and another address. An answer is begun (`pending`) before anything is sent and is `done` with the fields that went once the owner took it; a block that is pending or done is refused (409 `answered` with the fields that went, or `pending`) from any device, so the same block is never sent twice. A refusal cancels it; "not confirmed" (504) leaves it pending until it expires (two minutes), since the answer may have gone.
  - A chat block's answer rides the composer's `sessions/<key>/input` request with `block {entry, index, fields}` (`recordBlock`, wrapping every branch of `run`, a box's unit and a tower included; an operate session's `block` is ignored, and a test sends one). `GET api/answered/<unit key>` reads it back (`{done: [[entry, index, fields]], pending: [[entry, index]], unreadable}`); the page asks when it draws a log (one shared request, repeated when the last is older than 3 s). A document's record comes with its text (`GET api/doc/<cap>`: `rev`, `answered {done, pending, unreadable?}`).
  - The page keeps the live copy in memory only (`gui/blocklock.ts`, no storage): one cell per scope and block, shared by every drawing of it. While an answer is on its way every drawing is inert and says "Sending…" (a redraw does not find it open); when it ends, all drawings lock with the fields or reopen with the reason.
  - Storage errors never reopen a block silently. A record that cannot be written refuses to begin (500 `unsaved`, nothing sent); one that cannot be written after the send keeps the entry in memory and tells the page (`unsaved: true`); one that cannot be read starts empty and the page shows, under each open block, that whether it was answered could not be read (the server still refuses a block it knows is answered).
  - **Fail closed (round 4, BSR-F002).** The file is read as the house reads its records (`src/server/answeredfile.ts`: no link followed, `O_NOFOLLOW` and an lstat; a file of another account, a directory, or one over 32 MB is not read; a missing file is a new record, anything else unreadable) and held to a strict schema: `{v: 1, entries: [[key, state]]}` with a key of exactly the two shapes above (parts at most 4,096 characters, an index 0 to 4,095, the hash 16 hex digits), a state `pending` or `done` with text pairs, and a time that is a non-negative integer (clamped to the time of the load, so a planted entry cannot outlive the 90 days). One entry out of shape makes the whole record unreadable. An unreadable record is never overwritten: the first write moves the file aside (`answered.json.unreadable-<time>`), and if that fails nothing is written and nothing sent (500 `unsaved`); `unreadable` stays set for the life of the process, so the note stays under every open block, and a later write does not clear it.
  - **The page follows the record (round 4, BSR-F004).** A block a record showed as on its way (another device's answer, or a 504) opens again when a later record no longer lists it (the answer was refused, or expired); a block this page is sending itself stays pending until its own delivery ends, and an answered block never reopens. `gui/answered.ts` remembers each unit's entries, so an entry with no row at all is told so too. Interpretation of the tower's "fail to show the source state": the block is shown as the source has it (open), with that note.
- **Chips.** A chip shows the text it sends: when its text is not what its label reads as (`inlinePlain`), its label becomes that text (punctuation escaped, so it shows as written), so nothing goes out under the boss's name that the boss did not see (BS-F001).
- **The confirm step (round 4, BSR-F001).** The same rule for the kinds whose outgoing text has a name apart from what is drawn: a picked choice of a form whose `value` is not its label, a checklist item whose `name` is not its label, and a form question's `name` (the key of its line) that is not its label as drawn unless it is a plain identifier (`/^[A-Za-z0-9_.-]{1,40}$/`, such as `store`: the agent's own handle for the answer, which the boss does not assert; a key that is prose, has other punctuation, or is longer lands in the message as text and asks; a key that is its label as drawn was seen). Boss decision (tower, 2026-11-08). When the answer would carry any of them (`hidden` in `gui/blocks.ts`) the element's answer is not sent: the block shows a step under the element with the exact text `encodeAnswer` made (a `pre`), a Send button that sends that very text and a Back button (Escape too). One step at a time, and it goes by itself when the block is answered or locked from anywhere else. A form whose keys are handles or labels and whose picked values are shown goes at once; options, review, and chips are drawn with what they send. `encodeAnswer` and the package's elements are unchanged. 44 px controls on touch.

## Security

- No `pageUrl` hook: a review `page` item shows its one-line pointer. `imageUrl` resolves only through the host: in a document, a relative image path (letters and digits of any script, `_ .@+-`, no `..`, no `.`, no separator but `/`, a raster or svg extension) becomes the document's own capability route (`doc/<cap>/<path>`), which `docs.ts` serves for a Markdown document as images only, from the document's folder, under the same CSP `sandbox` as every `/doc/` response; in chat there is no image route, so none shows. The package's default (any http(s) or data image) is replaced.
- **Diagrams.** `diagramUrl` is not set: `pi-better-show/server` needs `beautiful-mermaid`, a new runtime dependency of the server bundle, and the manifest test allows `tsx` only. A Mermaid block shows its source with the package's note.
- Nothing from a block becomes HTML: elements build text nodes; the block code has no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, or `DOMParser` (a test greps for them and a mutation check writes through them). CSP is unchanged (`style-src 'self' 'unsafe-inline'`, the elements use constructed stylesheets).

## Look

The `--pbs-*` tokens have one owner, the views (docs/specs/2026-11-07-raven-view/spec.md §7): Standard maps them in `gui/style.css` `:root`, Geek in `gui/themes/geek/geek.css`, Raven Keep in `gui/themes/raven/raven.css`, and Zen in `gui/zen.css`, each dark with `color-scheme: dark`. A block takes them by inheritance from the view it is in (`tests/pbs-tokens.test.ts` guards that every view maps all of them and that `gui/pbs.css` declares none). `gui/pbs.css`, the block chunk's own sheet, keeps what §7 does not cover: the wrapper's layout, the note and dimmed states, and the 44 px touch rules (on a touch screen or a phone's width every control of every element is 44 px tall, `::part()` rules scoped to `.pbs-block`). Density is the host's `density` attribute (compact in the comms log, comfortable in a document), not a token.

## Round 2: contract v2 (pi-better-show 0.1.0 and later)

- **Listener.** The bridge listens to `doc-review:documents` (v1) and `better-show:documents` (v2), asks each once (`…-request`), keeps the two lists apart and relays both, v1 first (an id is one document: a later duplicate is dropped), the newest 32 when together they pass the hub's limit (each owner lists oldest first; BSR-F006). A v2 entry is `{id, kind blocks|html|text, display, reason, revision, onScreen, capability?, assets?}`; the relayed copy is marked `v: 2` and never has a path. `display` is shown as given. A `capability` or `assets` that is not the owner's own page server (`http://127.0.0.1|localhost|[::1]:<port>/<token>/doc/<id>/<name>` and `…/doc/<id>/`, no credentials, query, fragment, `..`, or encoded slash) is dropped by the bridge and refuses the whole entry at the hub. The v1 listener stays until pi-herdr-doc-review is archived.
- **Reading a v2 document.** The sb server fetches it from the capability (`docs.ts` `pull`: loopback only, no redirect, 5 s, 2 MB for a document, 8 MB for a neighbour) and serves it as a v1 one: `blocks` and `text` as the text of `GET api/doc/<cap>` (the card of a `blocks` document says `blocks`, a `text` one `text`, a v1 Markdown text document `blocks`); `html` in the same twice-sandboxed frame, with the owner's frame hook (`assets/frame.js`) removed, since no script runs there; neighbours (an HTML document's styles, fonts, images; a Markdown document's images) from the owner's `assets` URL, relative paths only, by the type of their extension. A document with no capability (its page server is off) cannot be read.
- **Answers.** The bridge turns a form for a v2 document into `better-show:answer {version 2, id, answerId, answer}` and relays `better-show:answer-result` as the v1 form result; a `text` document's answer is `invalid` without asking the owner; an HTML document's pi-answer form becomes an `Answer` too (`pi-kind` review or feedback is the kind). The package's own `answerId` replay still applies behind sb's. The round trip against the real extension is `tests/better-show-roundtrip.test.ts`.
- **Residuals.** (1) A v2 HTML page that needs a script (a TSX page, `piBetterShow.send`) does not run under this server's frame policy, as no v1 page ever did; its forms answer. (2) A v1 Markdown text document: the bridge answers `closed` for a form to any v1 document that is not HTML, and pi-herdr-doc-review refuses one too, so a block answer in such a document could never be delivered; the answer route now refuses it up front with that reason (BSR-F005) instead of blaming a closed document. v2 `blocks` documents take them, and v1 is going away. (3) The record is this server's: a box's unit is recorded here, by the key this server gives it, not on the box.

## Notes from task: the tree block (pi-better-show 0.4.0)

The package is pinned at exactly 0.4.0 (`package.json` and the lock; `NOTICE.md` names it and its fourteen elements). `tree` is a display block: an indented directory snapshot (`name/` for a folder, `{tags}`, ` # note`, `… N more`; spec `~/projects/pi-better-show/docs/specs/2026-11-08-tree-block/spec.md`).

- **Drawing.** Same path as every kind: `parse` finds it, `blocks.ts` makes the element of `TAGS.tree` (`pbs-tree`, defined by the package's `defineAll`) and feeds it the block's data at the host's density (compact in the chat, comfortable in a document). No new element registration, no new chunk: it rides the block chunk (`blockschunk.ts`), which grew by about 7.9 KB raw / 2.2 KB gzipped (the element, the tree parser, the text fallback the bundle carries).
- **Where sb had to learn the kind.** Two literal lists: `gui/mdbody.ts` `KINDS` (the hint that decides whether the block chunk loads at all: without `tree` a message whose only block is a tree stayed plain Markdown) and `src/blockcount.ts` `KINDS` (the server's upper bound on a document's block indexes: without it the answer to the block after a tree was refused as `no_block`). Tests derive both from `BLOCK_KINDS` now (`blocks-answer`, `blockcount`), so a kind the next bump adds fails there until sb counts it.
- **Display, not answerable.** `ANSWERS` in `blocks.ts` is the package's `INTERACTIVE_KINDS` (it was the same five kinds written out by hand), and the `pbs-answer` handler returns at once for a kind outside it: a display element that fired one (none does) would deliver nothing and lock nothing. A test holds `BLOCK_KINDS` to `DISPLAY_KINDS` plus `INTERACTIVE_KINDS`, so a new kind forces a decision about whether it is answerable. A unit whose box is away switches off the blocks that can be answered; a tree stays readable, its folders still open and close. The server needs nothing more: it never reads a block's kind (an answer carries its own, held by the owner), and a tree has no answer to record.
- **Text only.** A tree's names reach the element as text (the element builds text nodes), and sb makes no name a link, a route, or a file to open (the package's spec leaves clicking a file out of scope). A note takes the package's restricted inline Markdown, which would draw `[text](https://…)` and a bare `https://…` as anchors; the page does not offer a link in a snapshot an agent wrote, so `dataOf` hands the element a note whose links are their labels (and a bare address escaped so it stays text): bold, italic, and code are kept, a note with no link is the block's own string, untouched. This is the only place where a block kind differs from the others (a card body or an alert keeps its links).
- **Touch.** On a touch screen or a phone's width `pbs.css` makes a tree's rows (`::part(node)`) and its two bar buttons (`expand-all`, `collapse-all`) 44 px; a file's row is as tall as a folder's, since the part cannot tell them apart (a long tree is long on a phone). A test holds every part the sheet names to a part the element has.
- **Themes.** No tree CSS: the element's tags read `--pbs-ok`, `--pbs-note`, `--pbs-risk`, `--pbs-accent`, and `--pbs-muted`, which every view already maps. Read in Standard, Geek, Zen, and Raven Keep, on a desktop and at a phone's width, in a chat message and in a document card (`~/.local/share/sbd-review/better-show/tree-shots/`).
- **0.1.2 to 0.4.0, what else changed for a host.** The bus contract (`better-show:*`, version 2) is the same, and so are `parse`, `encodeAnswer`, `inlinePlain`, `configure`, `Answer`, and every element's events and parts. Added: `raw` on `BlockSegment` and `InvalidSegment`, `toText`'s `keep` and `lang`, `DISPLAY_KINDS`, `INTERACTIVE_KINDS`, `validateAnswer`, `optionName`, `TREE_TAGS`, `TREE_LIMITS`, `TreeData`, `TreeNode`, and the `pbs-tree` script. sb uses none of `raw`, `toText`, `validateAnswer`; a sb that read block kinds on its server could not use `validateAnswer` (it needs the parser, which the server does not ship). The extension loads its page server on first use and `show_doc` runs after the `write` beside it; an HTML or TSX page has the feedback panel, whose selection reports come from the owner's frame hook, which this server removes (the page runs no script).
- **Demo.** `gui/demo-blocks.ts` has a tree at the end of the document with every block kind (tags, notes, a folder deeper than two levels that opens because of a tagged file below it, one that starts closed, a `… N more` line) and one after the chat message's table.
