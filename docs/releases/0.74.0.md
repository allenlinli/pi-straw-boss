# pi-straw-boss 0.74.0

Not yet released.

## The tower opens the integrator

Todo #151 (the boss's choice of 2026-11-10: the box's tower opens the integrator itself, and an ally sends only the car slip). On a shared box, an ally's main had no integrator to own its trains: the ally run's `boss_open_main` for one was refused, since a sender gets one opened main. That limit is not widened. The tower now opens the project's integrator itself, on a car slip.

- **One door: `boss_open_main` with `role: "integrator"`**, in a run of the sb server, with the slip as the request and its sender. The server finds the slip itself, among the `call_tower` messages (`why=shared`) the run took from that sender, by the `head:` the request carries (a run is shown no event id, so the `forward: <event id>` of 0.73 could not be followed by itself). It finds the project's integrator or opens it, and forwards the slip as its sender wrote it, stamped `fwd` and `fwd-from`; nothing the run typed is forwarded.
- **The tower's own main.** The integrator's pane is marked `sb_opened_by=integ:<project>` and its tab and session are named `integ <project>`, so the new pi is of kind integrator before it is handed anything. It counts toward neither the workspace's two opened mains nor its sender's one. A tower opens at most 2 integrators in its workspace.
- **The project is the checkout's.** The opener reads it from the workspace's checkout: `integration.project` at the top of `apps.json`, else the folder name of the repository (every worktree of it reads the same). Another word from the run is refused, so a slip cannot be sent to another project's integrator, one app cannot get two integrators under two names, and made-up names cannot use up the workspace's two places. An integrator that works in another repository takes no slip, whatever its name; an ally run's open stays inside the project its team binds here.
- **Never two for a project.** An app whose trains a ledger already keeps under another project (`trains/<project>/<app>.json` in the state folder) is refused with that project's name. A live integrator of the project anywhere on the computer takes the slip (one a tower marked, or a main of kind integrator named `integ <project>`). A main opened for a teammate's device is never one, whatever name and kind it carries: its pane token keeps it out, and the route table refuses a slip for it. A marked pane whose pi has not joined, a marked main of another kind, and two mains that both answer as the integrator each refuse the open and say which. The opens of one project wait for each other across every tower, so two workspaces that take a slip at the same moment open one. The open is kept in no ledger: after an idle integrator closed, the next slip opens it again.
- **Integrators you already run stay.** The one-per-project rule is for the integrators the door opens. Where a project already runs integrators under names of their own (one per app, such as `integ FE2` and `integ v3` in one checkout: live mains of kind integrator in the tower's workspace or working in the checkout, unmarked by a tower and not opened for a teammate's device), the door opens nothing, counts none of them, and picks none. It answers with their names and the slip's event id, and the tower forwards the slip as in 0.73: `tower_reply` to the integrator that runs that app's trains, with `forward` naming that id, so the code stamps its sender. This is also the first time that forward can name its event: in 0.73 a run had no way to read the id. An ally run is given no id and forwards no slip there.
- **An ally's car slip.** The `call_tower` of a main an ally run opened reaches the ally runs of its device, never a local run. There the same call is the ally run's one door to an integrator: the server takes it only for a slip this run took from a main opened for its own device, and refuses everything else before the gate. Below `dispatch` it needs the boss's confirm, and the request has to be the slip exactly as it came, so the confirm shows the text that is forwarded. When such a main's slip reaches a local run instead (it named another workspace's tower, or its route was gone), the door refuses it by the main's pane token or any workspace's route table. The integrator gets no ally route, so its reports and trains go to the local runs; the forward also carries `origin=remote:<device id>`.
- **Refused.** A request with no slip, a slip of an app with no `integration` in the workspace's `apps.json`, a project word that is not the checkout's, a teammate's device as the sender, the merge train off, and `role: "integrator"` outside a run of the sb server.
- **Prompts.** `tower-run.md` sends a car slip through the door, forwards it with `tower_reply` and the door's event id where the project runs integrators of its own, and no longer tells the tower to open an integrator as a main and have it call `boss_duty`; `ally-run.md` sends a slip of a main it opened the same way and answers a request to open an integrator with that.

To move: nothing. Integrators you opened yourself keep their slips: several under names of their own (one per app) get them by the tower's forward, as before, and a single main named `integ <project>` (or one that took a broken integrator over) gets them from the door when it works in the project's repository. Only when you want the door to open the integrator of a project whose ledger is kept under another name than the repository's folder, add `"integration": { "project": "<that name>" }` at the top of that project's `apps.json`; until then that open is refused and names the ledger's project.
