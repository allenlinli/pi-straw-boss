## Kinds and tower runs on the ally view

Todo #150, from the boss's question on 11/10 about a box that runs a coordinator, an integrator and trains: the page's ally view drew none of them by kind, and the tower's runs read as agents that opened and closed by themselves.

- **A box's mains show their kind on the ally card.** Each row of a unit's *Mains* fold now says *coordinator*, *integrator*, *standing*, or *train* between the name and the state, in the words the local page uses (the same in every theme; icons still go by position). A main whose pane names no kind draws no word.
- **On the wire.** An entry of the `mains` in a box's `unit-status` gains an optional seventh field, `kind`, at most 16 bytes. The box writes it only to a controller whose fresh `caps` list the new `unit-status.kind` feature beside `unit-status.mains`; every other controller gets the six-field entries of before, so an older device reads what it read. The list is still the mains the controller may stop, not a wider one. The spec's "the ally board carries no role and no kind" is amended ([agent kinds §12](../specs/2026-11-09-agent-kinds.md#12-link-and-remote-devices)).
- **A tower's run is not a unit.** A tower wakes a short run for each message and stands by after it. A tower unit in its `running` or `waking` state now reads *run in progress*, with a tooltip that says it stands by between runs; *running* stays for a plain unit's `working`. On a box's operate base the finished runs (an ally run, an event run, the tower's own) are a closed fold, *Tower runs*, beside the agents' *Earlier runs*, and never rows among the agents.
