# pi-straw-boss 0.61.1

Not yet released.

## The notice for messages that wait says what waits, for whom, and until when (todo #122)

The Link button's notice for Straw Link messages that had not reached a tower read "Team X's inbox has 4 messages waiting: no tower is open on the project". It used a word the boss never meets (inbox), stated one cause as fact, and named no sender, age, workspace or deadline. It now reads, for example:

- **English:** "Team moldplan: box n2knna sent 4 messages, the oldest 3h ago, for the tower of workspace “MP Center”. They are not delivered yet; they go through as soon as the tower can take them, and the oldest is dropped on 11/13."
- **繁體中文:** 「團隊 moldplan：box n2knna 傳來 4 則訊息，3 小時前起就在等，要交給「MP Center」工作區的塔台，還沒送達。塔台能接手時就會自動送達；11/13 起會開始丟棄。」(one sentence serves one message and many, as zh-TW has no singular; 「3 分鐘前」 replaces 「3 分前」 everywhere an age shows)

- **Who, how many, since when.** The sender of the oldest message (several senders: that one and "and 2 more"), the count, and the age of the oldest in whole minutes, hours or days, so the notice changes only when its words do.
- **For which tower.** The label of the workspace the sender asked for when it is a workspace of this computer, else the project's folder name. A workspace id that is no longer open is never shown. Messages that wait for different towers are separate notices.
- **Until when.** The date the oldest message is dropped: its arrival plus the store's 7 days (`INBOX_MAX_AGE_MS`).
- **No word about a tower being open or closed.** To the boss a workspace's tower always exists; the copy says only that the message is not delivered yet. The pi notice of the same event (`Straw Link: a message from … is not delivered yet; it waits for the tower of …`) follows.
- **The notice that a message waited for an ally run** (more than 10 minutes) no longer says "inbox" either; the "waiting for an idle tower" notice already had no such word.

The notice has no button: the "Show towers" route would not make a tower take the message.

Data: the `inbox` alert's `data` is now `{count, from, others, since, drop, ageMin, workspace?, project}` (was `{count}`), and its id is `inbox/<team>/<id of the workspace asked for>/<state>`: a name that is no workspace here is not in it, so ghost names make one notice.

## An attended computer wakes the tower of a workspace it already has (todo #122, the boss's ruling of 2026-11-07)

To the boss a workspace's tower always exists, so a teammate's message no longer waits with a notice just because the tower of an existing workspace had not been started. Before, only an unattended computer did anything about it, and only for a `dispatch` sender.

- **Who and what.** A message from a teammate at `reply` or higher (a member with no `link.trust` entry is at `reply`, so every member qualifies; a sender who left the roster is dropped before this) makes the server give the tower to a workspace this computer already has: one with a pane inside the project, or the workspace the sender named (id, else label). It never makes a workspace or a base for it, moves no focus and types into no other pane. The one thing it may make is the tower's tab in that existing workspace, when the workspace has none (the boss confirmed this: a wake may add the tower tab). With no such workspace it makes nothing. A workspace name the sender wrote that is no workspace of this computer (or is the head or a sub workspace) costs no wake.
- **No storm.** One wake runs at a time per project and workspace asked for (by its id, so no made-up name adds one), a sender has at most 3 in flight, and the next try waits a minute after the last ended, then two, four, and so on: up to 30 minutes when it worked or found no workspace, 10 when it failed. A `none` is tried again at once when a workspace with a pane inside the project appears. With `towerRuns` switched off nothing is woken. A message that arrives while one runs adds nothing.
- **The link log** gets `tower-wake` and then `tower-woke`, `tower-wake-none` (no workspace) or `tower-wake-failed` (with the error) when the state changes, not at each try. It has no message text.
- **The notice appears only when the wake did not work.** While a wake runs, and for two minutes after the first that worked, there is neither a Link button notice nor a pi notice. After that:
  - *No such workspace:* "…This computer has no workspace for it to wake the tower of. Open the project's workspace and the messages go through." (「這台電腦上沒有可以叫醒塔台的工作區。開啟專案的工作區，訊息就會送達。」)
  - *Tower runs are switched off:* "…Tower runs are switched off on this computer, so nothing can wake the tower. Switch them on and the messages go through." (「這台電腦停用了塔台執行功能，所以沒有東西能叫醒塔台。啟用後訊息就會送達。」)
  - *The wake failed:* "…Waking the tower did not work (<reason>); it is tried again later." (「叫醒塔台沒有成功（<原因>）；稍後會再試。」). The reason is one of three plain sentences (the tower service is still starting; the project folder is missing or not allowed here; something went wrong, link.log has the details), never the server's own English.
  - *The wake worked but the tower has not taken the message in two minutes:* the plain copy above, on the page and in pi.
- **Unattended computers are unchanged:** only a `dispatch` sender opens a tower, and it may make a workspace. A failed wake of an attended computer is not told to the sender.

Data: the `inbox` alert's `data` gains `wake` (`"none"`, `"off"` or `"failed"`) and, for a failed wake, `reason` (`"service"`, `"project"` or `"other"`). The holder's `openTower` seam takes a fourth argument, `"open"` or `"wake"`, and answers `"no-workspace"` for a wake that found no workspace.
